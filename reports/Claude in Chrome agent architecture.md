# Build the browser core as a tool server

Claude in Chrome is, at its core, a **Manifest V3 extension that acts as a privileged tool executor**: it drives the user's real, logged-in tabs through `chrome.debugger` (CDP) for trusted input and screenshots, injects an accessibility-tree walker that hands the model short `ref_N` element handles, confines the agent to its own Chrome tab group, and exposes the same roughly 22 tools to Claude Code over MCP through a native-messaging host or a cloud relay. Anthropic's own product direction (the side panel now runs as a Cowork session by default) and the open-source field (Nanobrowser, Playwright MCP's extension bridge, browser-use) have converged on one pattern: **one tool-calling loop, a deterministic browser-control layer with fail-closed element refs, an accessibility-tree text snapshot as the default observation, screenshots on demand, and layered permission gates enforced in the executor rather than the prompt**. The research literature backs each piece. Element-ID grounding over a pruned tree beats raw HTML and pixels on DOM pages, pruning the observation alone gained AgentOccam about 10 points on WebArena, and prompt injection stays unsolved: even Anthropic reports non-zero residual attack success and leans on system-layer classifiers you will not get from the raw API. For this repository the most important finding comes from its own code. The side panel is a client of a local **opencode server, which already owns the agent loop, renders permission forms and MCP elicitations, and names MCP tools `<server>_<tool>`**. So "chat plus browser control" and "expose the browser to external CLIs via MCP" are the same engineering problem. Build the browser core once, as an MCP tool server backed by the extension, and opencode becomes its first client.

## Claude in Chrome splits into an executor, a ref system and a bridge

Claude in Chrome went from a 1,000-user pilot in August 2025 to general availability on every paid plan on **26 August 2026** ([Piloting Claude in Chrome](https://claude.com/blog/claude-for-chrome); [GA post](https://claude.com/blog/claude-in-chrome-generally-available)). The only detailed teardown is sshh12's analysis of extension v1.0.56 (March 2026), so read the internals below as a snapshot of one version. It describes a React side panel that ran the Anthropic SDK in the browser, OAuth PKCE auth, and automation through `chrome.debugger.attach(tabId, "1.3")`. Screenshots came from CDP `Page.captureScreenshot`, downscaled to a token budget (`pxPerToken: 28`, `maxTargetPx: 1568`), with the scale stored so model coordinates map back to the viewport. The extension hid its own overlay before every screenshot and click ([sshh12 gist](https://gist.github.com/sshh12/e352c053627ccbe1636781f73d6d715b)). Element refs come from `window.__generateAccessibilityTree`, injected with `chrome.scripting.executeScript`. It maps tags to ARIA roles, derives accessible names from `aria-label`, placeholder, `<label>` or text, and stores each element as a `WeakRef` in `window.__claudeElementMap` under a persistent `ref_1`, `ref_2`... id. The `find` tool sent that tree to a secondary Sonnet call for semantic matching ([sshh12 gist](https://gist.github.com/sshh12/e352c053627ccbe1636781f73d6d715b)). Tab state lived in a `TabGroupManager` backed by `chrome.storage.local`. When tabs changed, the new tab context went into the conversation as a `<system-reminder>`. Old base64 images were compacted into placeholders at about 25 MB.

The current MCP contract, read live from this session's `claude-in-chrome` server on 2026-11-05, shows how those internals surface as tools. The table groups them by function.

| Group | Tools | Design point worth copying |
|---|---|---|
| Tab scoping | `tabs_context_mcp`, `tabs_create_mcp`, `tabs_close_mcp` | Agent acts only on tabs in its own group; each conversation creates its own tab |
| Navigation | `navigate` (url, `back`/`forward`) | Auto-creates a group tab when none exists |
| Observation | `read_page` (filter `interactive`/`all`, depth, `ref_id` subtree, `max_chars` 50k), `find`, `get_page_text` | Truncation is explicit, with a note giving the full size; `find` returns at most 20 refs |
| Action | `computer` (13 actions incl. click variants, type, key, scroll, drag, hover, `scroll_to`, `zoom`, `screenshot`), `form_input`, `file_upload`, `upload_image` | `ref` or coordinate; coordinates are always in full-resolution space even when `scale` shrinks the image |
| Diagnostics | `read_console_messages`, `read_network_requests`, `javascript_tool` | Logs are cleared on cross-domain navigation |
| Throughput | `browser_batch` | Sequential, stops on first error, per-item permission check |
| Multi-browser | `list_connected_browsers`, `select_browser`, `switch_browser` | Devices addressed by `deviceId`; user confirms pairing in Chrome |

Two details matter for your design. First, every mutating action now carries an `action_summary` that must "state the effect only… no passwords or other secrets". It is the natural input for both a permission prompt and an action classifier. Second, the tool surface keeps two targeting paths side by side: refs for semantic DOM work (`form_input`, `file_upload`, `scroll_to`) and pixel coordinates for anything the tree cannot express. That is the hybrid the research literature recommends.

The CLI connection uses two transports. Locally, Claude Code registers a native messaging host (`com.anthropic.claude_code_browser_extension`; on Windows under `HKCU\Software\Google\Chrome\NativeMessagingHosts\`) that Chrome reads only at startup. For multi-device and remote sessions there is a cloud relay at `bridge.claudeusercontent.com`, which is why the extension must be signed into the same organization as the CLI ([Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)). The documented failure modes there translate directly into your bridge design. Windows named-pipe conflicts (`EADDRINUSE`) appear when two CLI sessions hold the pipe. Two native hosts registered for one extension ID do not fall through to each other ([issue #24507](https://claudeissues.com/issue/24507-bug-chrome-extension-native-messaging-host-conflict-claude-desktop-claude-code-o)). JavaScript dialogs block all commands. A long idle stretch lets the MV3 service worker die with "Receiving end does not exist" ([Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)). The MIT clean-room clone makes the chain explicit: `Claude Code <-stdio MCP-> mcp-server.js <-TCP/pipe-> native-host.js <-native messaging-> extension` ([open-claude-in-chrome](https://github.com/noemica-io/open-claude-in-chrome)).

Safety is layered rather than a single control. Users pick Manually approve, Automatically approve (each action screened for exfiltration or injection; the Cowork default) or Skip all approvals. Site permissions are granted once or always. Purchases, account creation, card or ID data, untrusted downloads, permanent deletion, trades, and following instructions found in web content are prohibited in every mode ([Permissions guide](https://support.claude.com/en/articles/12902446-claude-in-chrome-permissions-guide)). In v1.0.56 the permission types were concrete (`NAVIGATE`, `READ_PAGE_CONTENT`, `CLICK`, `TYPE`, `DOMAIN_TRANSITION`, and others), domains were classified into categories cached for five minutes, and **the tab's domain was re-checked before each mutating action to catch mid-action redirects** ([sshh12 gist](https://gist.github.com/sshh12/e352c053627ccbe1636781f73d6d715b)). The measured effect of the layers is large. Injection attack success fell from 23.6% to 11.2% at launch ([Piloting Claude in Chrome](https://claude.com/blog/claude-for-chrome)) and to **1.4% for Opus 4.5** under an adaptive attacker in November 2025 ([Prompt injection defenses](https://www.anthropic.com/research/prompt-injection-defenses)). At GA, trained probes on tool results plus an action classifier that checks each action against the original request reached 0% for Sonnet 5 and Opus 5 and 0.3% for Fable 5 on a new red-team set ([GA post](https://claude.com/blog/claude-in-chrome-generally-available)).

## Comparable agents and the papers converge on refs, pruning and single loops

The open systems that publish their internals agree with Anthropic's design almost point for point. Nanobrowser, now rebuilt on WXT, says outright: "One agent, not the old planner and navigator: one loop per conversation." Its browser-control layer is deterministic and contains no model. `chrome.debugger` is "the only route to CDP". Refs are tied to the exact node and are "valid only in the document where the agent saw it", returning a typed error otherwise. Before any input it checks that the target is visible, stable, enabled and not covered. It dispatches real input once and never retries after dispatch. Each result reports separately whether input was dispatched, whether the page reacted, and whether the expected state was reached ([nanobrowser AGENTS.md](https://raw.githubusercontent.com/nanobrowser/nanobrowser/master/AGENTS.md)). Its permission table is the clearest public template. Reads, link clicks, scrolls and tab switches always proceed. Submit, send, delete and upload ask first in the default mode. Pay, password entry and access grants always go back to the user ([nanobrowser README](https://github.com/nanobrowser/nanobrowser)). Playwright MCP treats its accessibility snapshot as "better than screenshot", warns that you "can't perform actions based on the screenshot", and hides coordinate tools behind `--caps=vision` ([playwright-mcp README](https://github.com/microsoft/playwright-mcp)). Chrome DevTools MCP lets every input tool take `includeSnapshot` so a fresh snapshot comes back with the result and saves a round trip ([tool-reference.md](https://raw.githubusercontent.com/ChromeDevTools/chrome-devtools-mcp/main/docs/tool-reference.md)). browser-use dropped Playwright for raw CDP because of the extra relay hop and state drift, and keys each node on `target_id`, `frame_id` and `backend_node_id` so input reaches nested cross-origin iframes ([browser-use: Playwright to CDP](https://browser-use.com/posts/playwright-to-cdp)).

The academic record explains why. Grounding, not planning, is the bottleneck. SeeAct completed about 51% of live tasks with oracle grounding, its best automatic method trailed by 20 to 30 points, and textual element choices outperformed Set-of-Mark overlays on dense pages ([SeeAct](https://arxiv.org/abs/2401.01614)). Mind2Web's prune-then-choose approach and Agent-E's "DOM distillation" plus "change observation" both beat raw HTML ([Mind2Web](https://arxiv.org/abs/2306.06070); [Agent-E](https://arxiv.org/abs/2407.13032)). **AgentOccam added no new architecture, only pruned observations and a smaller action space, and reached 43.1% on WebArena, +29.4 points over its vanilla agent** ([AgentOccam](https://arxiv.org/abs/2410.13825)). OSWorld found that text trajectory history helps while screenshot-only history does not ([OSWorld](http://osworld-v1.xlang.ai/)). Online-Mind2Web is the reality check. A search agent that scored 51% on WebVoyager managed 22% on live tasks. **About 57.7% of Operator's errors were filter or sort mistakes**, and failed trajectories run about twice as long as successful ones, padded with repeated actions and pop-ups. An LLM judge agrees with humans 85 to 87% of the time, while agents' own success claims include hallucinated completions ([Online-Mind2Web](https://arxiv.org/html/2504.01382)).

The safety literature sets the ceiling on what a third-party extension can promise. Pop-up attacks reached about 86% success against vision agents, and telling the agent to ignore pop-ups did not help ([Pop-up attacks](https://arxiv.org/abs/2411.02391)). Invisible form fields stole specific PII up to 70% of the time ([EIA](https://arxiv.org/abs/2409.11295)). WASP found agents partially hijacked in up to 86% of cases, saved only by "security by incompetence", a margin that shrinks as models improve ([WASP](https://arxiv.org/abs/2504.18575)). Brave showed that faint text inside screenshots injects instructions that bypass text sanitization, so a screenshot-only design is not a safe harbor ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). The durable defenses are architectural. CaMeL derives control flow only from the trusted user request and solves 77% of AgentDojo tasks with provable security, against 84% undefended ([CaMeL](https://arxiv.org/abs/2503.18813)). Willison's "lethal trifecta" (private data, untrusted content, outbound communication) describes a logged-in browser agent exactly, and he calls 95% detection a failing grade ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). One caveat sharpens this for you. Anthropic's GA safety numbers include server-side probes and an action classifier. A secondary report puts Opus 4.8's raw browser hijack rate at 31.5% before safeguards and 0.5% after ([pulse.bot](https://www.pulse.bot/ai/news/anthropics-browser-agent-got-hijacked-315-of-the-time-before-safeguards-engaged-08ce0929-21bd-42f1-ab59-1f78400b4f7f/)). If that figure holds, most of the robustness sits in a layer your extension must rebuild for itself.

## Eighteen recurring failures have known fixes

Most of the engineering effort goes into the browser's sharp edges, not into the model. The failures below show up in Anthropic's own docs and issue tracker, the comparable projects, and the Chrome API references. Each has a known fix.

| Problem | Cause | Fix |
|---|---|---|
| Service worker dies mid-task | 30 s idle, 5 min per event, fetch with no response in 30 s ([SW lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)) | Keep loop out of the SW; rely on keepalives: attached debugger (118+), WebSocket (116+), native port (105+); persist run state in `chrome.storage.session`/IndexedDB |
| "Started debugging this browser" infobar; detach on Cancel or DevTools | Inherent to `chrome.debugger`; `onDetach` reasons `target_closed`, `canceled_by_user` ([debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger)) | Attach lazily, only for agent tabs; detach when idle; on `canceled_by_user` stop re-attaching and tell the user |
| Screenshot hangs ~30 s on background tab | Hidden tabs stop producing compositor frames ([issue #78533](https://claudeissues.com/issue/78533-claude-in-chrome-page-capturescreenshot-times-out-30s-on-any-tab-whose-visibilit)) | Activate the tab before capture, short timeout, fall back to `captureVisibleTab` (max 2/s, active tab only) ([tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)) |
| Tab frozen by alert/confirm/beforeunload | Dialogs block events and evaluation ([Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)) | `Page.enable` on attach; handle `Page.javascriptDialogOpening`, report text to the model, then accept or dismiss per policy |
| Stale ref acts on the wrong node | DOM re-render or navigation | WeakRef registry per document; fail closed with typed `STALE_REF` error ([nanobrowser](https://raw.githubusercontent.com/nanobrowser/nanobrowser/master/AGENTS.md)); invalidate on `onHistoryStateUpdated` |
| Clicks miss by a constant offset | Device-pixel vs CSS-pixel vs sent-image scaling ([computer use docs](https://platform.claude.com/docs/en/docs/agents-and-tools/tool-use/computer-use-tool)) | Send images at CSS-pixel viewport size, store scale per screenshot id, map back before `Input.dispatchMouseEvent` (CSS px, `clickCount:1`) ([Input.pdl](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Input.pdl)) |
| Near-misses on small targets | Downscaled image | `zoom` region capture, or click by ref |
| Agent overlay visible in screenshots | Own UI in page | Hide overlay before capture and click; restore after ([sshh12 gist](https://gist.github.com/sshh12/e352c053627ccbe1636781f73d6d715b)) |
| Elements in cross-origin iframes unreachable | OOPIFs are separate targets | `Target.setAutoAttach({flatten:true})`, called again in each child session (not recursive); route by `sessionId` (Chrome 125+) ([debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger)) |
| React inputs ignore set values; sites reject synthetic events | Controlled inputs; `isTrusted:false` | Native value setter plus `input`/`change` for `form_input`; escalate to CDP `Input.insertText`/key events |
| Model-written JS blocked by page CSP | Isolated world cannot `eval`; MAIN inherits CSP ([chromium-extensions](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/W2J8_81NzkM)) | CDP `Runtime.evaluate` or `chrome.userScripts.execute`; gate the tool as sensitive |
| File upload opens a native picker the agent can't see | OS dialog | Never click file buttons; set files by ref (`DOM.setFileInputFiles` with bridge-provided paths, or in-page `DataTransfer`) ([Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)) |
| SPA "navigation" never finishes | No load event; network never idle | Race `webNavigation.onCompleted`, `Page.lifecycleEvent` networkIdle, and a 500 ms DOM-quiet observer under a hard 10 to 15 s cap |
| Popups and `target=_blank` escape the agent | New tabs outside scope | `tabs.onCreated` with `openerTabId` in the agent set, then add to the agent's group ([tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)) |
| Restricted pages fail | `chrome://`, other extensions, the Web Store, policy-blocked hosts | Expose only `navigate` there, as Claude in Chrome does ([sshh12 gist](https://gist.github.com/sshh12/e352c053627ccbe1636781f73d6d715b)) |
| Context bloat and image-limit errors | ~1,000 to 1,800 tokens per screenshot; stricter limits past 20 images; oversized tool-result images are rejected, not resized ([vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)) | Text snapshot by default; keep the last 3 screenshots; prune in batches to preserve cache ([computer use docs](https://platform.claude.com/docs/en/docs/agents-and-tools/tool-use/computer-use-tool)) |
| Loops, repeated actions, false "done" | Greedy agents and hallucinated success ([Online-Mind2Web](https://arxiv.org/html/2504.01382)) | Repetition detector, per-run step budget, verify-after-act, optional judge on completion |
| Bridge conflicts and stale host config | Pipe already held; Chrome reads host manifests only at startup | One rendezvous owner with multi-client fan-out; versioned, backward-compatible wire protocol (store releases lag ([Playwriter notes](https://tomevault.io/tome/remorses/playwriter))) |

## Recommended architecture: opencode runs the loop, the extension owns the browser

**Where the loop runs.** The literature offers three placements: the side panel (Claude in Chrome classic, Nanobrowser), the service worker, or an external harness that treats the extension as a tool executor (Claude Code, and increasingly Cowork). Your codebase has already chosen the third. The side panel streams an opencode server's session over SSE, renders its tool timeline (`lib/opencode/tool-info.ts` already has a `browser` entry and formats MCP tool names), and answers its consent forms and MCP elicitations (`lib/opencode/forms.ts`). A second, extension-side LLM loop would duplicate model configuration, history, compaction and permissions, and it would give "chat" and "browse" two different brains. Keep **one loop, in opencode**, with browser tools simply available, as Nanobrowser does. The model answers plainly when no tool is needed, so you need no router. Inject the active tab's URL and title as context on each user turn, the same move as Claude in Chrome's `<system-reminder>` tab context. One caveat: opencode's MCP configuration format and permission hooks come from the opencode docs, not this research, so verify them against server 2.2.5 before committing.

**Topology.** The extension cannot listen on a port, so a small local process has to sit in the middle. Ship a Node package, `opencode-browser-mcp`, that opencode launches as a local stdio MCP server. It opens a WebSocket on `127.0.0.1`, and the extension's background service worker dials in and reconnects in a loop, as Playwriter and the Playwright MCP bridge do ([Playwriter notes](https://tomevault.io/tome/remorses/playwriter); [cdpRelay.ts](https://glama.ai/mcp/servers/@maywzh/playwright-mcp/blob/4890b9d509ede4dd662b7f0c4f3718cec207081e/src/extension/cdpRelay.ts)). Choose WebSocket over native messaging first. It needs no per-OS registry install and no Chrome restart, it keeps the service worker alive on Chrome 116+, and your extension already pairs with loopback services by token. Harden it with a token handshake from your existing pairing flow and an `Origin: chrome-extension://<id>` check. Add native messaging later if you need OS-level caller identity. **Expose your own high-level tool protocol, not raw CDP**, so the permission gates stay enforceable inside the extension even when Claude Code or Codex is the caller.

**Executor placement.** Put all CDP traffic, tab-group state and the ref resolver in the background service worker. Debugger event listeners live in whichever context called `attach`, so keeping them in one place survives multiple windows and panel closes. While a task runs, the attached debugger and the bridge socket keep the worker alive (Chrome 118+ and 116+). Inject the DOM snapshot as a WXT `defineUnlistedScript` bundle via `scripting.executeScript({files})` in the ISOLATED world, so its registry persists across calls within a document. The side panel stays a view. It shows live tool progress, approval prompts and a "share this tab" control, and it never runs the loop.

**Tool set (about 14 tools).** Start from Claude in Chrome's contract. Anthropic's tool-design guidance favors fewer, higher-level, namespaced tools with actionable errors and explicit truncation ([Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)), and it also keeps your tools familiar to models tuned on that surface. The set is `tabs_context`, `tabs_create`, `tabs_close` and `navigate` for scope. Observation is `read_page` (interactive or all, `ref_id` subtree, `max_chars`, truncation notice) and `find`. Implement `find` first as text or regex search over the snapshot, Playwright's `browser_find` approach, which costs no tokens, and add an LLM-backed semantic mode later. `get_page_text` returns main content. `computer` covers click, type, key, scroll, hover, drag, `scroll_to`, screenshot, zoom and wait by `ref` or coordinate, with `action_summary` required on every mutating action. `form_input` and `file_upload` work by ref. `console` and `network` read logs. `javascript` is gated as sensitive. `batch` is sequential, stops on the first error, and checks permission per item. Every mutating tool returns a compact change report (URL or title change, new or removed refs near the target, any dialog). That is Agent-E's change observation and DevTools MCP's `includeSnapshot` folded into one result.

**Element refs.** Phase one uses the content-script walker: pierce open shadow roots and same-origin frames, keep visible or interactive or semantically named nodes, assign `e12`-style ids through a `WeakMap<Element,id>` plus a `Map<id,WeakRef>`, and emit an indented role-and-name tree. Ids should be stable across snapshots of the same node and scoped to the document, failing closed when stale. Before acting, scroll the node into view, re-read its rect, and confirm with `elementFromPoint` that it is not covered, or return an "obscured" error. Phase two upgrades the ref key to `{targetId, frameId, backendNodeId}` from CDP `DOMSnapshot.captureSnapshot`, which flattens shadow DOM and adds paint order for occlusion in one round trip ([DOMSnapshot.pdl](https://chromium.googlesource.com/devtools/devtools-frontend/+/HEAD/node_modules/devtools-protocol/pdl/domains/DOMSnapshot.pdl)). That is the browser-use identity that makes OOPIFs work.

**Observation strategy.** The default turn is a pruned text snapshot. Screenshots are on demand, plus one automatically after a state-changing batch. Send JPEG at the CSS-pixel viewport size (1280x800 costs about 1,334 tokens, against a 4,784-token cap for a DPR-2 PNG) and keep the scale with each screenshot id. Keep the last three images and replace older ones with text placeholders. Expose `screenshot` only when the selected model supports vision, as Nanobrowser does. Prompt for verify-after-act, because Claude "sometimes assumes actions succeeded" ([computer use docs](https://platform.claude.com/docs/en/docs/agents-and-tools/tool-use/computer-use-tool)).

**Permissions and safety gates.** Enforce gates in the executor. Opencode's prompts and the side panel are only the UI. Classify every call into five tiers. Read (snapshot, text, screenshot, scroll, tab switch) always proceeds. Navigate proceeds within approved sites and asks on first visit to a new domain. Mutate (click, type, form_input) proceeds on approved sites. Consequential actions (submit, send, delete, upload, download, `javascript`, cross-domain navigation after reading a sensitive site) ask every time. Hand-off actions (payment, password or OTP entry, CAPTCHA, account creation, granting OAuth access) always go back to the user. Re-check the tab's domain right before dispatch. Wrap all page-derived text in explicit untrusted-data delimiters. Break the trifecta's exfiltration leg with a per-run origin set: once a run has read a site the user marks sensitive, navigation or form submission to any other origin needs approval. An optional cheap-model action check (does the `action_summary` serve the user's original request?) approximates Anthropic's action classifier, but treat it as defense in depth, not a guarantee.

**Context management.** History and compaction already live in opencode. Your job is to keep tool outputs small: hard `max_chars` caps with "N more chars, narrow with `ref_id` or `find`" notices, interactive-only snapshots by default, change reports instead of full re-snapshots, and screenshot pruning in batches so prompt caching survives. Add a run step budget and a repeated-action detector in the executor that returns an error after the same action fails twice on the same ref.

**Manifest.** Add `debugger`, `tabs`, `tabGroups`, `scripting`, `webNavigation` and `<all_urls>` host access, with `downloads` and `userScripts` optional, and set `minimum_chrome_version` to `125` for flat sessions. `debugger` cannot be optional, and it draws the heaviest Web Store review ([OpenCLI PR #415](https://github.com/jackwener/OpenCLI/pull/415)). If you plan a store release, consider a lite build that uses only `scripting` and drops `debugger`.

## Conclusion

The central decision in this research is not which tools to copy. It is noticing that the user's extension already sits on the far side of an agent harness. Anthropic is moving Claude in Chrome the same way, toward a shared Cowork loop with the extension as executor. So the leanest path to "chat that can also drive the browser" is to make the extension the best possible MCP browser server, not a second agent. That single bet means phase 2 already delivers chat-plus-browse and phase 5 is nearly free. It also forces the right security posture: once Claude Code, Codex or any future caller can reach the same socket, the gates have to live in the extension, because no caller's prompt or permission system can be trusted to enforce them.

Two uncertainties should shape priorities. Anthropic's near-zero injection numbers depend on server-side probes and classifiers that a self-built extension does not inherit. Your architecture therefore needs to limit blast radius (tab-group scoping, tiered gates, an exfiltration rule) more than it needs to detect attacks. And the head-to-head evidence for tree-versus-screenshot-versus-hybrid observation comes almost entirely from GPT-4-era models. Make the observation mode a configurable executor policy and measure it on your own live task suite rather than fixing it in the protocol.
